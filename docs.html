SpecPort docs / agent protocol

A spec should make the next action obvious—and the result verifiable.

This is the working standard for turning a thought into a buildable contract, handing it to an agent, and ending with evidence a human can inspect. The agent may implement; the owner keeps intent, boundaries, acceptance, taste, and the final ship decision.

01 / Install & export

Put the same evidence protocol in the agent’s workspace.

Install the published package as a development dependency. Then export the two packaged playbooks into the native skill directory used by your agent host.

01

Project dependency

Install the CLI

npm install --save-dev @specport/specport

Requires Node.js 20 or newer. Prefer the project-local binary through npx --no-install specport so the run is tied to the version in the repository.

02

Inspect first

List the packaged skills

npx --no-install specport skill list

The package includes specport-repo-to-spec and specport-spec-to-production. Read the bundle before exporting it into a shared project.

03 / Host integration

Export the playbooks without silently overwriting local instructions.

Use the directory your host actually loads. The examples below use Codex; replace .codex/skills with .claude/skills or the host’s documented native location when needed.

npx --no-install specport skill export specport-repo-to-spec --out .codex/skills/specport-repo-to-spec
npx --no-install specport skill export specport-spec-to-production --out .codex/skills/specport-spec-to-production

Boundary: a skill is an instruction bundle, not permission to approve, publish, deploy, or invent missing requirements. Existing export directories are protected unless the owner explicitly chooses --force.

02 / Write the standard

A useful spec is a contract, not a longer prompt.

Write for a cold reader who was not in the original conversation. Name the user job, the outcome, the boundaries, and the evidence that would change the decision. Preserve what is known, what is inferred, and what still needs a human answer.

Every accepted spec declares

The decision surface

  1. Owner + user/jobWho owns the decision, and who is trying to accomplish what?
  2. OutcomeWhat observable change should exist when the work is done?
  3. Scope + non-goalsWhat is included, explicitly excluded, or forbidden?
  4. ConstraintsPrivacy, compatibility, performance, dependencies, permissions, and operating limits.
  5. Acceptance criteriaScenario-shaped, ID’d, observable results with evidence and risk.
  6. VerificationExact commands, fixtures, environments, and what each check does not prove.
  7. Taste + human reviewNamed reviewer and a product-specific rubric for the real medium.
  8. Release + rollbackArtifact, target, compatibility, recovery path, and ship authority.

Keep truth labels visible

Four kinds of statements

ObservedDirectly supported by a file, command, runtime, test, or artifact. Add a source locator.
InferredA reasoned interpretation of observations. Cite the observations and mark it for human confirmation.
UnknownMaterial information that was not found or not run. Keep the question and its blocking stage.
AcceptedA named human decision with owner, date, version, boundary, and any accepted risk.

An agent summary is not evidence. If a command was not run, record it as not run.

A readable source shape

Keep the contract portable in SPEC.md.

This outline is a starting point, not permission to fill unknown decisions with defaults.

# Product or change name

Status: draft — human confirmation required
Owner: [named human]

## Intent
- User / job: [who needs what]
- Outcome: [observable result]
- Non-goals: [what this does not do]

## Scope and constraints
- In scope: [bounded paths, surfaces, or behavior]
- Constraints: [privacy, compatibility, dependencies, permissions]
- Forbidden behavior: [explicit unsafe or out-of-scope actions]

## Acceptance
- AC-001: Given … when … then …
  Evidence: [artifact, output, runtime observation]

## Verification
- `npm test` — proves [checks], does not prove [taste / release / security]

## Taste and human review
- Reviewer: [named human]
- Rubric: [product-specific live review]

## Release, rollback, unknowns
- Artifact / compatibility: [target]
- Rollback: [last known good + recovery owner]
- Unknowns / next actions: [open decisions]

03 / Run the loop

Move one gate at a time. Re-open downstream gates after every change.

The loop below is the compact operating protocol. Use the packaged skills for the detailed handoff and keep the artifacts beside the repository so another agent or human can resume without replaying a chat transcript.

  1. 00

    Capture the thought

    Start with the user job and desired outcome.

    Use specport spec create notes.md --out SPEC.md for a brief or specport spec bundle . for a repository handoff. Preserve the source and label missing intent as unresolved.

    draft
  2. 01

    Ground the draft

    Separate repository evidence from product intent.

    Read the baseline and evidence ledger. Use [OBS-*], [INF-*], and [UNK-*] references so a cold reader can trace every claim.

    observed
  3. 02

    Accept the contract

    Ask the owner to accept, revise, or reject the intent.

    Run specport spec check SPEC.md --json for structure, then create the human-owned contract and run specport spec validate .specport/contract.json --json. Neither command creates acceptance by inference.

    human gate
  4. 03

    Lock the handoff

    Make the accepted inputs reproducible.

    Run specport spec lock SPEC.md --out SPEC.lock and check specport spec drift SPEC.md --lock SPEC.lock --json before implementation and before the final receipt.

    locked
  5. 04

    Implement in scope

    Let the agent work only against accepted paths and criteria.

    Trace each change to an acceptance criterion. If the implementation reveals a new requirement, stop and return to the owner instead of silently expanding the contract.

    bounded build
  6. 05

    Verify the candidate

    Run checks on the exact final candidate and save the outputs.

    Run the project’s declared tests, lint, typecheck, build, runtime smoke, and relevant failure paths. Then use specport coverage with an explicit expected scope or pinned receiver; inventory alone is not proof.

    evidence
  7. 06

    Review the real medium

    Have the named human perform the user job.

    For UI, inspect the live flow; for audio, listen; for writing, read in context; for operations, exercise recovery. Record the rubric, observations, decision, identity, and timestamp.

    human gate
  8. 07

    Guard and decide

    Bind the spec, evidence, scope, and candidate into one receipt.

    Run specport spec guard with the contract, acceptance, verification, taste, lock, and explicit comparison basis. A pass means the supplied evidence is identity-bound; the human still owns release, rollback, publish, deploy, and ship.

    not ship authority

When a gate blocks

Return a fact-shaped status, not a hopeful summary.

STATUS: BLOCKED
GATE: G <name>
EVIDENCE: <exact artifact or command output>
REASON: <fact, not a guess>
OWNER DECISION NEEDED: <specific question>
RESUME WHEN: <observable condition>

04 / Best practices

Make the spec easy to challenge before it becomes expensive to build.

01

Lead with the job.

Describe who needs what and why before naming a feature or implementation.

02

Make acceptance observable.

Prefer scenario criteria with IDs, expected results, evidence, and risk over adjectives like “seamless.”

03

Write the forbidden path.

State what the agent must not change, upload, infer, approve, or silently expand.

04

Say what a check cannot prove.

A test, map, lock, coverage result, or guard receipt each has a narrower boundary than “done.”

05

Keep unknowns alive.

Missing facts become questions with owners and blocking stages; they do not become conventional defaults.

06

Version the handoff.

Keep the exact spec, contract, evidence, tree identity, provenance, release artifact, and recovery path together.

SpecPort can help prove

Relationships between declared artifacts and the exact candidate.

  • A draft preserves its source and exposes unresolved decisions.
  • A lock and drift report compare the intended handoff inputs.
  • Coverage identifies whether the final tree matches an explicit scope or receiver.
  • A guard receipt binds supplied evidence to one repository identity and candidate.

SpecPort cannot decide for you

Whether the product is correct, safe, tasteful, or ready to ship.

  • It does not infer product intent from code or a passing test.
  • It does not execute project code, replace security review, or perform taste review.
  • It does not approve a contract, publish, deploy, or grant ship authority.
  • It does not turn an inventory-only scan into merge proof.

05 / Agent preamble

Give the agent a short instruction it can carry into every task.

Copy this into the host instruction layer, then point it to the project’s actual SPEC.md and evidence paths.

SPEC-PORT / WORKING RULES 
Before changing code, read SPEC.md and state the user job, outcome, scope,
non-goals, constraints, acceptance criteria, verification commands, human
review, release target, rollback, and unknowns.

Keep observed, inferred, unknown, and accepted claims separate. If a material
decision is unresolved, stop and ask the owner. Implement only accepted scope.

Run the declared checks on the final candidate and save their outputs. Run
specport coverage with an explicit scope or receiver, then complete the named
human review and specport spec guard.

Report exact evidence, limitations, and the next owner decision. Never call a
summary, passing test, or inventory scan a ship decision.
